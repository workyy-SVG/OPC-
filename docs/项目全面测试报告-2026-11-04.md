# 项目全面测试报告

## 结论与覆盖范围

项目的示例主流程可运行，但采购台账、汇总在途及库存快照还不是一个统一的业务账本。真实门店使用前，应先解决库存一致性、连续更新销售数据和重复采购问题，再扩展功能。

- 现有完整测试：**101 passed，25.52秒**。
- 独立启动最新版Streamlit，健康接口返回ok、首页返回Streamlit HTML；测试服务随后已停止。
- 额外执行核心函数和页面边界探针，复现下文12项需要处理的问题；其中第3项是有提示的设计限制，而非无提示的数据删除。
- 实际运行默认留出期实验，5商品、选参期2010-05-02至05-31、留出期2010-06-01至06-30。准备数据1.08秒，实验10.18秒。该时间只代表本机单次运行。
- 千问、DeepSeek Key在当前测试环境均不可用，没有发起付费请求。不能据此判断用户Streamlit部署中的Key状态。
- 未进行真实浏览器视觉/手机适配测试、线上缓存复现、真实店铺试用或生产负载测试。AppTest不是浏览器测试；HTTP健康也不能替代页面功能测试。

不能保证一次审计发现所有缺陷。本报告区分实际复现、设计约束和待验证事项，不能理解为“全系统已无其他问题”。

## 优先处理：库存与交易正确性

### 1. 已确认采购未进入补货清单的在途计算【高；已复现】

位置：`purchasing_ui.py:55`、`purchasing_ui.py:77`、`app.py:532`。

- 采购页用台账剩余采购替换`on_order`，补货清单却仅读取库存表`on_order`。
- 核心探针：确认采购20件后，台账口径建议0件，清单仍建议20件。
- 页面探针：UCI商品85123A确认1044件采购后，库存表在途仍为0，返回清单仍建议1044件。
- 保存当轮采购页也没有立即重算上方建议，可能继续显示保存前数量。

影响：同一商品在不同页面得到相互矛盾的采购提示，容易重复采购。

建议：统一库存位置查询，台账与原有在途先做明确归属；保存采购后统一重新计算。不要简单把两份在途相加或任意相互替换。

### 2. 新采购收货会扣减可能属于其他订单的汇总在途【高；已复现】

位置：`core/purchasing.py:157`。

复现：库存表已有100件其他在途；新增10件采购未增加该汇总在途，收到这10件后，现货增加10，原100件在途却变成90。

影响：台账和库存表数量越操作越不一致，后续建议有误。当前`max(0,on_order-qty)`隐藏了归属问题。

建议：以采购明细及其收货流水计算在途，外部原始在途作为单独明细管理，收货只能冲减关联采购。

### 3. 更新销售数据会清空当前库存、采购、收货流水【高；已复现的设计限制】

位置：`app.py:152`，特别是`save_sales`清理列表。

页面探针：已有1笔采购，成功核验更新后的销售文件，`purchases`、`inventory`被移出当前会话，收货流水也在同一清理列表中。

页面已经提示“更换数据会开启新记录”，因此这是已声明的行为。适用于更换演示数据集，但不适合店主每天补充销售的正常操作。既有磁盘快照可能仍存在，这不等于磁盘上所有记录都被删除；当前UI无法自动继续原经营账本。

建议：分开“新建经营工作区”和“更新当前店铺销售”；后者按稳定业务键合并销售，保留采购和库存，再做库存对账。必须先区分取消、退款与实际退货。

### 4. 通用订单导入仍套用UCI专用取消规则，中文状态列未被映射【高；已复现】

位置：`core/ingest.py:28`、`app.py:277`附近字段选择。

- `order_id=CUST-1001,status=completed,qty=2`，被统计为取消订单，有效销售0。
- `order_id=1001,qty=2,订单状态=取消`，被统计为有效销售1，取消0，因为可选中文状态列没有映射到`status`。

影响：实际店铺销量可能被错误剔除，也可能把取消交易算作销售。

建议：按来源配置规则：UCI保留其C前缀约定，用户CSV优先使用显式状态。提供状态、行号等可选字段映射及中文状态值归一化；不要把退款直接当作实物退回。

### 5. 空订单行编号能绕过疑似重复检测【高；已复现】

位置：`core/ingest.py:9`、`core/ingest.py:36`。

复现：两行完全相同记录，不含`line_id`时提示2条疑似重复；只增加一个值均为空的`line_id`列，仍计入两行销量，却不再提示任何疑似重复。

影响：多出的空列改变质检结果，重复销售影响补货。

建议：按每行是否有有效行编号选择去重策略，而不是按整个文件是否存在该列；空白字符也须归一化。无可靠业务键的重复仍应提示人工确认，不能直接删除。

## 次优先：异常输入与重复操作

### 6. 非法库存日期可保存，随后让采购页崩溃【中；页面已复现】

位置：`app.py:513`、`app.py:519`、`purchasing_ui.py:131`附近。

复现：库存日期填`not-a-date`，点击保存显示成功；再进入采购页，出现`Unknown datetime string format`异常。

建议：保存前复用库存校验，先验证所有修改，成功后一次应用。采购页也应捕获已存坏数据，提示回库存配置修正而非崩溃。

### 7. 登记采购没有防重复提交机制【中；页面已复现】

位置：`core/purchasing.py:34`、`purchasing_ui.py:70`附近。

复现：勾选确认并登记后，确认框保持选中；再次点击登记得到第二条采购。核心函数对完全相同内容也总生成新UUID。

重复采购有时是有意操作，因此不能只按商品和数量硬性去重。

建议：为一次提交生成稳定请求编号，网络重试使用同一编号；成功后清空确认状态。明确“再建一笔相同采购”的操作，避免与重试混淆。

### 8. 覆盖区间排除全部交易仍显示核验成功，没有说明交易被排除【中；页面已复现】

位置：`app.py:310`、`core/demand.py`。

复现：CSV只有2025-01-01的一笔5件销售，确认覆盖2025-02-01至02-02。页面显示有效1条、未发现问题；日销量合计0，另有31个未知日期。

用户可以有意选择部分区间，但当前没有区间外记录计数，质检成功和实际进入计算的销量不一致，容易误解。

建议：显示“区间内/外订单行数及销量”、未知日期和有效计算商品数。完全没有区间内交易时明确警告或要求再次确认。

### 9. 输入CSV含系统问题字段会中断质检【中；核心已复现】

位置：`core/ingest.py:33`、`core/ingest.py:38`。

复现：带`reason_code`列的CSV出现一条非法数量，构造问题记录时报`dict() got multiple values for keyword argument 'reason_code'`。`row_no`、`hint`也有同类冲突。

建议：原始输入字段和系统诊断字段分开命名或分层存储。UI会捕获部分异常，但用户仍无法正常核验这份文件。

### 10. 商品编码/订单编号未统一处理首尾空格【中；核心已复现】

位置：`core/ingest.py`与`core/inventory.py`。

复现：订单中的`001`和`001 `被保留为两个商品；库存导入却会去掉编码首尾空格。销售和库存采用不同规则。

影响：同一商品拆成两份，或库存无法匹配；原始表看起来可能没有区别。

建议：统一所有业务键的规范化，同时保留原始值供追溯，不能删除前导零。归一化造成冲突时显式提示。

### 11. 备份缺少采购商品与库存商品的交叉校验【中；核心已复现】

位置：`core/purchasing.py:180`。

复现：库存只有001，备份含UNKNOWN商品采购，`load_workspace`仍成功恢复。UI目前只比较恢复前后的库存商品集合，不校验采购商品属于其中。

影响：恢复出不可正常收货的采购，后续只能看到错误提示。当前收货函数会拒绝缺失库存商品，并未观察到该路径错误增加现货。

建议：恢复前校验采购、收货、流水与商品集合的一致性；备份加入店铺/数据来源标识，避免仅因SKU集合相同就混入另一套记录。

### 12. 数字通过校验却超过页面上限，且浮点转整数会失真【中；页面及核心已复现】

位置：`core/inventory.py:28`附近、`core/ingest.py:18`附近、`core/purchasing.py:integer`。

- 数量字符串9007199254740993经过float后变成9007199254740992。
- 库存CSV现货为`1e30`能导入，随后数字输入控件报`value must be <= (1 << 53) - 1`，页面中断。

这是异常大数边界，不代表普通小店数量会常见触发，但应在导入阶段拒绝，不能先保存再让页面崩溃。

建议：用十进制/整数语义解析，设合理的业务上限，并小于前端安全整数范围；所有入口使用相同校验器。

## 进一步优化与已知限制

这些事项不能混称为已经发生的业务错误：

1. **持久化与会话恢复**：采购工作区没有账户或固定店铺身份；新会话靠备份恢复，Community Cloud本机磁盘不保证长期保留。正式运营需数据库、店铺隔离与自动备份。对于公开数据Demo可继续保留当前方式，但必须说明边界。
2. **每日AI额度不是服务商级预算**：SQLite能在本实例内原子计数，现有并发测试通过。磁盘重建会清零，多实例不共享，也不能限制同一Key在其他程序的调用。若用于长期控制费用，需持久计数并配置服务商预算/告警。
3. **AI商品识别只收到候选SKU**：真实单据常用商品名称、供应商货号，缺少别名映射会让模型返回未匹配。建议提供最小必要的名称/条码/供应商编码字典，并让用户确认。不能声称当前识别效果已实测。
4. **AI草稿来源与新输入未绑定**：草稿作用域只有商品集合和库存日期；用户修改描述、照片或参考日后，旧草稿仍会显示。建议标明草稿对应的原始输入摘要，输入变化时提示重新生成，并重置确认状态。
5. **“AI已就绪”仅检查Key存在**：并未检查Key地域、模型权限、余额。建议改为“已读取Key，连接待验证”，再提供显式、计入额度的连接测试。不得悄悄发送业务数据作为探测。
6. **核心入口的防御校验不一致**：直接调用`run_replay`会接受分数销量，忽略`coverage_status=unknown`；`recommend`遇重复日期会抛异常。正常导入一般会得到整数且未知日为NaN，所以这不等于当前页面必然产生错误结果。仍应统一为可识别的业务校验，以免未来API接入绕过前端。
7. **实验计算性能与缓存**：本机默认留出期运行10.18秒；增加数据后可能影响交互。可按数据指纹、日期、目标和规则版本缓存纯计算，避免每次重复选参；不要缓存用户混合的会话状态或不同店铺私有数据。
8. **留出期证据强度**：单一历史数据源、一个留出窗口及固定有限参数网格，不能证明普遍最优。下一步可增加预先固定的滚动留出窗口，报告所有结果及库存/满足率取舍。当前默认结果可复现，不将这是验证局限写成计算失败。
9. **热更新与浏览器静态资源**：已加部分模块兼容处理，但AppTest不下载浏览器JS。之前截图中的动态模块加载失败，仍需要在真实部署、强制刷新与不同浏览器中验证。
10. **文档滞后**：README开头仍称“五个页面”，已有多个新页面；历史验收记录也有旧测试数和版本。应区分历史记录与当前验证，避免把旧状态写成现在的状态。

## 推荐修复顺序及验收标准

1. **先统一库存事实来源**：解决第1、2项，明确采购、收货和外部在途归属。验收：确认采购后各页面库存位置一致；一笔收货只冲减其关联采购；库存守恒。
2. **再做经营工作区与增量销售**：解决第3、7项。验收：下一天销售导入后采购与流水仍保留，重复导入/提交不重复入账；更换店铺另建工作区。
3. **统一导入及保存校验**：解决第4至6、第8至12项。验收：取消语义按来源处理、空行号重复可见、异常输入不能落库、编码规则一致、错误备份不应用。
4. **最后补线上验证与体验**：真实Key联调、浏览器/手机、持久化、AI草稿状态及实验性能。均应单独记录验证环境，不将本地测试通过等同于生产验收。
